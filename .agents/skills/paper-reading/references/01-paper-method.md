# 论文阅读方法

## 分析链

```text
目的
  -> 主体
    -> 旧瓶颈
      -> 关键动作
        -> 机制链
          -> 证据链
            -> 技术债 / 边界
```

先回答：

1. 研究目的：这项工作要把什么瓶颈、成本或能力缺口，变成什么可用收益？
2. 阅读主体：本次真正要解释的是论文、机制、系统、模型家族、数据集、benchmark，还是一个技术瓶颈？
3. 旧瓶颈：它出现前为什么做不到？
4. 关键动作：它到底改了什么？
5. 证据边界：哪些来自论文、哪些来自 repo、哪些只是推断？

这条分析链用于阅读和核验，不要求每一环都成为网页上的独立章节。

## 默认篇幅与取舍

- 默认让读者约 5–8 分钟抓住主线，正文以约 1,500–2,200 个中文字为目标。图注、表格和折叠内容也计入阅读负担；来源列表、元数据、交互文案和用户既有评论不计入。
- 简单论文可以更短，不为达到字数补内容。超过约 2,500 字时先删重复背景、次要实验和实现细节；如果继续压缩会失真，保留必要解释。用户明确要求的深入版本不受此目标约束。
- 内容入选的标准：删除它是否会影响对贡献、机制、证据强度或适用边界的判断？不会影响的，默认留待后续交流。
- 不把省下的正文搬进大段折叠区、附录、图注或额外卡片。保留原文链接，让追问可以回到来源。

## 核心版组织

按当次论文组织自然段与小标题，围绕以下问题展开，不逐章复述原文：

| 读者要知道什么 | 默认呈现 |
| --- | --- |
| 解决什么，最值得记住什么？ | 一句具体研究目的，紧接一句核心判断；必要时补 2–3 个互不重复的要点。结论在图之前。 |
| 关键改动为什么有效？ | 简短旧瓶颈 → 核心改动 → 预期作用，集中解释最重要的 1–2 个设计选择，区分作者解释与实验证明。 |
| 哪些证据值得信？ | 通常选 2–3 项决定性结果，优先用一张小表；包括能改变判断的消融或反面结果。 |
| 哪些结论不能外推？ | 通常保留 2–3 个最重要的限制、代价或未验证前提，并说明它们如何影响论文价值。 |
| 如何回到原文？ | 给出论文、官方 repo 等实际使用的来源，关键判断就近标明章节、图表或页码。 |

- 首屏避免副标题、研究目的、总览图和要点各讲一遍同一个结论。
- 数字保留指标含义与方向、比较对象及关键评测条件；相对提升与百分点分开，作者报告与本页推断分开。不能为压缩省掉 oracle 选优、验证集参与训练、开环/闭环等影响解读的条件。
- 若原文没有足够定量证据，呈现已有论证及其缺口，不为凑结果数量编造数字。
- 默认省略完整相关工作、逐模块说明、全量 benchmark、完整消融、复现参数和公式推导；其中若有直接支撑或推翻核心判断的部分，仍需保留。

## 术语、公式与图

- 只解释读懂主线所必需的术语，首次出现时用中文加一句直觉说明；不为每个英文词创建 `term-bridge` 或独立小节。
- 默认用语言讲清优化目标与作用。只有公式本身是理解创新不可替代的一环时才展示，通常至多一个核心公式；说明它回答什么问题、所展示符号的含义、关键约束和直觉，不展开推导。
- 通常用一张 SVG 讲清核心改动，图放在核心判断之后；它也可直接承担机制图，避免再画一张重复总览。只有第二张图能显著减少文字或澄清独立的关键关系时才增加；简单内容可不用图。
- 图只保留必要的输入、关键动作、输出和约束。`read-guide` 用 1–2 句说明关键关系，正文补充图中没有的信息，不逐节点复述。

## 后续交流与深入版

- 普通追问先在对话中回答当前问题，必要时回查原文；不自动把每轮回答写进网页。用户明确要求更新正文或处理网页标记时，按 HTML 契约写回。
- 公式推导、实现参数、完整消融、相关方法对比等，在被问到时围绕该问题展开。公式深入解释按“解决什么问题 → 符号 → 约束与直觉 → 推导 → 与论文动作的关系”组织。
- 一个标记回答只解释当前标记；个人评论保持独立，不能当作已证实结论。
- 如有明确值得追问的内容，可在页尾列最多 2–3 个具体问题，仅列问题，不预写长答案或为凑数添加通用问题。
- 用户明确要求全面深读时，围绕需求扩展相应内容；仍以核心判断开篇，不机械补齐所有章节。

## 自检

- 只读开头，能否说清研究目的与核心判断？只读正文，能否解释关键改动为何针对旧瓶颈？
- 是否每项重要判断都有来源或明确标为推断？证据是否保留了会改变判断的条件、代价和反例？
- 删除某段、某图、某个术语框后不影响理解或判断的，删去；重复数字和图文重复优先合并。
- 是否仍有逐章复述、完整教程、无必要公式或大段折叠附录？有则按用户需求收缩。
- 稳定锚点与评论是否保留，可见标题是否帮助读者理解，而非展示内部分析步骤？
