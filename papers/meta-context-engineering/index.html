BI-LEVEL OPTIMIZATION · AGENTIC SKILL EVOLUTION · CONTEXT ARTIFACTS

Meta Context Engineering

以往 Context Engineering 往往先由人规定“反思—整理—追加”流程，再让模型往固定容器里填内容。这篇论文把更上游的问题也交给搜索：什么上下文结构合适、怎样从 rollout 学、何时删减、何时停止，先写成可执行 skill，再让 skill 与最终 context 一起演化。

Haoran Ye、Xuning He、Vincent Arak、Haonan Dong、Guojie Song 北京大学 · 通讯作者 Guojie Song 稿件日期 2026-01-27 · arXiv v2 · 46 页
研究目的

把 Context Engineering 从“在人工写死的 harness 中优化一份 prompt / memory”提升为双层优化：外层学习一套会指导上下文工程的 skill，内层执行这套 skill，把训练 rollout 转化为文件、知识库、检索器和组合逻辑；目标是摆脱 GEPA 式过度简写与 ACE 式不断追加这两类结构偏置，让不同任务自己长出合适的上下文形态，并在性能、长度、迁移和训练成本上接受验证。

核心结论

第一，MCE 的创新对象是 Context Engineering 的“学习算法”。上下文不再等同于一段 prompt；它被写成 context function，由静态文件与动态检索、过滤、组合算子共同构成。skill 则是生成和更新这个函数的可执行规范。

第二，最有说服力的结果不是“越长越好”，而是“长度与结构应随任务变化”。FiNER 的两个强 context 只有 1.5K 与 20K tokens，LawBench 与 USPTO50k 却长到 44K 与 86K；症状诊断长出 1,440 行路由器，法律任务反而把 context 从 88KB 收缩到约 30KB。

第三，完全 agentic 的基础层已经贡献了大部分收益，skill evolution 提供的是进一步校准。FiNER 离线消融中，无 skill 的基础代理为 73%，完整演化为 75%，ACE 为 71%；这支持双层设计，但也说明“演化 skill”相对强基础层的直接增量目前只有 2 个百分点，且只在一个任务做了完整消融。

第四，这是一套受验证集约束的有限搜索，不是开放世界里的无限自我进化。实验只运行五个 epoch，以单个 offspring 的 (1+1)-ES 选择 best-so-far；在线设置无法迭代演化 skill，长轨迹信用分配、推理密集任务、安全执行任意代码等问题仍未被解决。

READING OBJECT

不要把 skill、context artifact、context function 和 agent harness 混成一件事

CONTEXT ENGINEERING（上下文工程）

英译中：系统地选择、组织和调用推理时输入，使冻结的模型在下游任务上取得更高效用。

怎么理解：它优化的是推理时模型“能看到什么、按什么顺序看到、由哪些程序动态生成”，不是更新 LLM 权重。论文强调可解释、部署快、模块化以及不发生参数层灾难性遗忘，但这些是方法特征，不等于 context 天然可靠。

CONTEXT FUNCTION（上下文函数）

英译中：从当前 query 映射到实际送入模型的 context 的函数。

怎么理解：它由静态组件 ρ 与动态算子 F 组成。Markdown 规则、知识库、案例文件属于 ρ；检索、过滤、格式化和组合代码属于 F。于是“context”既可以是一段常量文本，也可以是按问题运行的程序结果。

CE SKILL（上下文工程技能）

英译中：告诉基础代理“如何表示、学习、验证和更新 context”的可执行规范。

怎么理解：它可以是一个含 SKILL.md、脚本、模板、校验协议与检索逻辑的目录。skill 是学习过程，不是最后塞给 generator 的领域知识；同一任务的 skill 会随验证反馈继续变化。

CONTEXT ARTIFACT（上下文产物）

英译中：基础代理执行 skill 后真正产出的文件与代码。

怎么理解：例如 reasoning-chains.md、tag-reference.md、症状路由器或 retrieve_context.py。artifact 承载“学到了什么”；skill 规定“怎样从 rollout 学到它”。论文的 co-evolution 指二者在迭代中相互影响，而不是两者使用同一个优化变量。

AGENTIC CROSSOVER（代理式交叉）

英译中：由元代理阅读任务、历代 skill、执行产物和分数后，选择性重组成功部件并修复失败模式。

怎么理解：它没有固定的“取两个父代各一半”规则。代理可以检查整个历史目录，判断过拟合、欠拟合、冗余或遗漏，再写出一个新 skill；因此它更像有记忆的设计评审，而不是字符串拼接。

FAILURE CHAIN

同一套“反思—整理”流程换到不同任务，偏置会从捷径变成瓶颈

偏置会随任务反转，所以“一个 SOTA harness”不等于通用解

FiNER 需要密集 XBRL 长尾规则和精细消歧，ACE 的反复反思有优势，GEPA 压得太短；Symptom2Disease 的 train/test 语义相近，多样例 ICL 反而很强，过度抽象会抹掉症状差别；LawBench 的长案件事实又会被庞大 playbook 干扰，此时 GEPA 的简洁反而成为优点。论文由此提出：不应先选定一种 harness 再跨任务复用，而应把 harness 的领域部分封装为可学习 skill。

“给代理更多自由”本身不是方法，验证反馈才把自由变成搜索

如果基础代理可以随意写文件和代码，却没有训练 / 验证分离与 best-so-far 选择，它可能只是在训练样本上造出更复杂的记忆。MCE 的元代理显式检查 train–validation gap：FiNER 的 skill 从具体 pattern 转向错误驱动的语义原则；症状任务在验证率已到 88% 且 gap 仅 1% 时学会设置停止条件；LawBench 则把 88KB context 收缩到约 30KB。

证据边界：“没有一个固定 harness 普遍最优”得到五个任务上基线排名反转和附录 case study 的支持；但 MCE 尚未覆盖开放式推理、长程工具代理或真实生产流量，因此不能据此断言每个 Context Engineering 问题都需要双层演化。

MECHANISM

外层挑“怎样学”，内层学“给当前 query 看什么”

第一层对象不是字符串，而是由静态组件和动态算子组成的函数

公式拆解 · Eq. 1–2
c(x) = (Fk ∘ ··· ∘ F1)(x; ρ)
c* = arg maxc∈C J(c)

这两式回答：一次推理真正使用的 context 怎样由 query 生成，以及普通 Context Engineering 在优化什么。

x
当前 query；不同 query 可以触发不同检索与组合路径。
ρ
静态组件集合，如 system prompt、知识库、规则、示例和代码资源。
F₁…Fₖ
动态算子，如检索、筛选、排序、格式化和组合；按顺序构成 context pipeline。
c(x)
最终提供给冻结 generator 的推理时 context，而不是模型参数。
J(c)
任务目标；监督任务可由损失定义，RL 设置可由期望 reward 定义。
直觉读法：常量 prompt 只是 c(x)=ρ₀ 的最简单特例；RAG 是一个检索算子；MCE 允许基础代理把文件和代码组合成更一般的 c。论文实验为了与基线公平，最终仍把 generator 接口限制为一次 query→context 检索。

双层目标把“学习程序”与“学习结果”分开

公式拆解 · Eq. 3
s* = arg maxs∈S Jval(cs*)
s.t.   cs* = arg maxcs Jtrain(cs; s)

这条式子回答：怎样选出一套能让基础代理学出高验证表现 context 的 skill，而不是只挑训练集上最好看的 context。

s / S
一个 CE skill 以及可搜索的 skill 空间；它定义表示、学习、脚本和校验过程。
cs*
基础代理在 skill s 指导下、利用训练 rollout 得到的最佳 context function。
Jtrain
内层训练目标，推动 context 修复当前 rollout 中的错误。
Jval
外层验证目标，决定该 skill 产生的 context 是否值得保留。
类比机器学习：c 像学到的参数，s 像架构加训练算法；区别是底层 LLM 已冻结，外层搜索的对象是自然语言指令、目录、脚本和 context 操作程序。

技能演化的实质，是让工程粒度、自治程度和停止条件跟任务一起变化

论文总结了三个反复出现的变化：其一，skill 会在严格流程与高度自治之间切换；其二，会根据任务复杂度和 generator 容量选择简短规则或详细知识；其三，会利用 train / validation 信号识别过拟合。FiNER 的最佳 skill 采用八阶段错误驱动泛化，并组织 reasoning chains、semantic principles 与 tag reference；症状任务则把“不要再加规则”本身写成方法条件。

实现上有两个代理，但 generator 仍保持冻结且接口刻意受限

论文用 Claude Agent SDK 实例化元代理和基础代理，默认 agentic model 为 MiniMax M2.1；generator 与 reflector 主要是 DeepSeek V3.1，AEGIS2 因安全 guardrail 场景改用 Qwen3-8B。基础代理可以调用 DeepSeek、访问受角色权限约束的工作目录，并最终实现一个 query→context 的 callable interface。这个限制使 MCE 能与现有 CE 基线公平比较，也意味着实验还没有检验一个会持续浏览文件、调用多轮工具的 generator。

TECHNICAL DEBT & BOUNDARIES

“Meta”“Evolution”“Self-Improvement”都成立，但每个词都有明确边界

第一，89.1% 与 74.1% 是相对基座增益的平均，不是平均正确率

五个任务混用了 accuracy、Micro-F1 与 F1，且基座差异很大：USPTO 从 6% 到 20% 会产生很大的相对比例。论文的摘要还报告相对 SOTA agentic CE 方法提升 5.6–53.8%、平均 16.9%；判断实际任务价值时，应优先看 Table 1 的原始分数与对应基线。

第二，完整双层设计只在 FiNER 做了拆解，且 skill evolution 的净增量为 2pp

完全 agentic 的基础代理在没有 skill 时已经达到 73%，超过 ACE 的 71%；完整 MCE 为 75%。这证明元层不是零贡献，却还不能说明五个领域的大部分增益都来自 agentic crossover。固定 skill 离线甚至只有 71%，说明“有一份 skill”本身不保证更好，关键仍是验证驱动的演化。

第三，在线 MCE 没有在线演化 skill

在线评测是单遍处理，完整迭代式 skill evolution 不适用；论文使用按任务说明预先生成的 fixed skill，基础代理持续积累已处理实例。更微妙的是，skill-less 变体在 Symptom、Law 与 AEGIS2 的原始分上高于 fixed-skill MCE，尽管 fixed-skill MCE 的跨任务平均相对增益更高。

第四，数据规模是受预算约束的子集，表格没有多随机种子与置信区间

FiNER 为 200/100/100，USPTO 为 50/30/100，Symptom 为 200/50/212，LawBench 为 200/50/100，AEGIS2 为 400/128/140。单个样本就可能改变 1 个百分点左右的 accuracy；论文没有给 context evolution 的随机种子方差或显著性检验。

第五，13.6× 与 4.8× 是 FiNER 的系统级观测，不是算法复杂度定理

MCE 通过批量分析、脚本和并行 LLM 调用避免 ACE 的逐实例反思，因而 1.9 小时完成五 epoch；但 wall-clock 会受 API 延迟、最大并发、缓存与实现影响。论文没有报告五任务总 token、美元成本、agent step 数或能耗，无法据此断言所有任务都能同倍率加速。

第六，公平对照控制了数据与 rollout budget，却没有完全控制 harness 自由度

基线获得不低于 MCE 的训练预算，并使用相同初始 context；但 MCE 可以写程序、批量处理和构造任意文件结构，而 GEPA、DC、ACE 按原始 harness 运行。这恰好是论文要比较的系统能力，却意味着结果不能归因于某一个 crossover 算子。用 MiniMax M2.1 替换 ACE reflector / curator 后分数从 70% 降至 67%，排除了“只是换了更强模型”的简单解释，但没有消除全部架构与计算差异。

第七，文件与代码自由带来安全面，论文只给权限边界，没有安全评测

基础代理能够写 Python、调用其他模型、编辑检索程序；元代理也能读取迭代历史并生成可执行 skill。论文说明读写权限按角色和迭代严格限定，但没有测试恶意训练样本、prompt injection、依赖供应链、越权读取或生成代码的沙箱逃逸。生产部署时，skill 评价必须同时包含安全与资源约束，而不能只看任务分。

第八，作者明确承认它更适合知识获取与模式匹配，不一定胜过推理型 harness

五个 benchmark 的核心是领域知识、分类与格式化；对需要多轮试错、错误修正和系统反思的推理任务，人工设计的 harness 已经很契合。复杂长轨迹还需要细粒度 credit assignment，而批量式 CE 可能看不清哪一步导致成败。这与“通用 CE 框架”并不矛盾，但限制了当前证据的外推范围。

第九，这轮“演化”是五 epoch、单 offspring、固定 evaluator 下的 best-so-far 搜索

历史可被完整读取，skill 也确实跨轮变化，因此 evolution 不是修辞；但没有群体多样性、长期开放式积累、跨任务 skill 迁移或 evaluator 自身演化。验证集一旦偏置，元代理会更有效地优化这个偏置。未来工作提出同时演化 context utilization skills、利用 progressive disclosure 组合跨域 skill，这些仍是路线图。
