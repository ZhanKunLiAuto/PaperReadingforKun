Harness²

把“如何改进智能体”也做成可积累的经验

Ruiyao Xu 等 · 37 页2026-10-09 · 用户提供的 PDF 版本

Harness² 的主要贡献是把任务内的运行环境改进，和跨任务的改进经验积累，连接成一条可执行流程。基础模型不更新参数；系统先观察一次真实执行，再分别提出通用运行策略与领域策略的修改，实际试跑，综合行为证据生成下一版 harness。任务完成后，留下可执行改动及其适用条件，供后续任务有选择地检索。因而这里“递归”的重点是改进过程本身获得经验，并不是模型可以不受约束地重写一切。

论文有说服力之处，是在不同模型、代理框架和工作型任务上测量了这条流程，而且不向改进器提供隐藏评分。最需要克制的结论则是：没有评分反馈，不等于系统拥有可靠的自我验证能力。试跑轨迹和产物可以暴露工具错误，却也可能共同继承错误前提；最后的选择器仍可能挑错结果。较少的最终执行步数也不能抵消为提出、试跑和综合额外消耗的全部计算。

先分清三层对象

模型负责理解、提议和执行，其权重固定。执行 harness H是围绕模型的可编辑运行配置，包含系统提示、护栏、记忆、技能、工具指导、脚本、子代理配置和中间件插件。改进 harness R规定怎样观察和修改 H。论文把 H 的改变放在单个任务内，把经验库的更新放在任务之间。

可编辑文件并非只有一段 system prompt。例如，一个技能可以规定怎样调和多个互相矛盾的业务文件，脚本可以把反复手工操作变成确定性检查，中间件可以改变工具使用的运行过程。论文允许的编辑面是预先划定的；阶段提示、决策规则和模型权重并不随每个任务任意重写。

每个新任务从共同的 H₀ 出发，不是直接继承上个任务的整套最终配置。继承的是经过索引、可检索的经验，内容包括采用的 harness 改动与 EXPERIENCE.md 中的条件、理由和支持证据。这种区别很关键：一项任务上有效的强约束，不必成为下一项任务的默认负担。

问题为什么需要两层改进

固定 harness 的困难在于，任务差别往往不只是答案内容差别。写网页需要查看渲染结果，做电子表格需要校验跨表一致性，处理专业业务材料需要尊重特定来源优先级。统一提示可以覆盖常见习惯，却很难预先包含所有领域检查。直接让模型“反思并改提示”又缺少对改动后果的观察，容易把一个听起来合理的建议当成有效机制。

Harness² 的因果链是：参考执行暴露具体行为 → 两种职责产生互补修改 → 在相同任务环境里运行候选 → 根据实际轨迹综合 → 把有用经验保存为未来可调用资源。这里的试跑并不等于拿到标准答案；它提供的是行为证据，例如是否遗漏输入、有没有重开文件核验、工具调用是否失败、最终产物是否满足可见要求。

论文的制片业务示例把人员表、日程和预算的核对组合起来：领域分支提出来源层级、数值格式等规则，通用分支强调盘点输入和重新打开输出验证。作者报告该示例评分从 43.1 升至 77.8。它说明修改可以落到可执行过程，但只是案例；不能从单例推出这些规则对任意业务任务都有效。

一次 Φ 更新如何工作

参考运行得到轨迹和交付物后，提议阶段分别产生 invariant-scope 与 domain-scope 候选。前者处理计划、工具、上下文和委派，后者处理专业程序、约束与知识。候选在新的容器中试跑，避免直接沿用已有环境副作用。Composer 看到修改差异、轨迹和产物，处理冲突，并决定生成后继版本、采用某一候选或保留原配置。该后继版本仍需实际执行。

k 是宽度还是深度，取决于实验配置

并行方案先产生 k 份参考执行，以及两种职责各 k 份候选；k 个综合器各自看到完整候选证据池，分别形成后继并执行。这是一次群体更新的宽度。顺序方案则把 Φ 接在上一版本之后，沿链累积证据，k 表示改进深度。论文分别研究两种扩展，不能把所有 k = 5 的结果理解成进行了五轮自我修改。

k = 1 不需要额外选择器；k > 1 时，选择器看到匿名交付物和任务材料，不知道来源 harness，也看不到隐藏评分。它只能返回某个已生成结果。记号 H* 表示流程最终采用的版本，不表示由真实分数证明的最优版本。

训练、资源与防止评分泄漏

该方法没有梯度训练。主要实验由 GLM-5 或 Gemini 3.5 Flash 执行，配合 OpenCode 或 Codex 框架；默认编辑器是 Claude Opus 4.8 high，另有同模型编辑器实验。每次执行最多 200 个 turn、3,600 秒。评测相关反馈被隔离；非法修改树重试一次，仍失败则回退。经验积累使用的是此前任务的运行证据，不是隐藏测试得分。

实验证据：有效改进与计算成本要同时看

WorkBuddy 使用代码 40、网页 35、办公 25 个测试任务；JobBench 使用 34 个测试任务；Harvey Legal Agent Benchmark（LAB）使用从完整集合分层抽取的 100 个测试任务。不同基准分别采用确定性检查和模型评审、加权业务量表、法律逐条标准，因此其分值不能跨表视为同一种成功率。任务流打乱后运行三次，主表报告均值与标准差。

经验复用的证据与回顾性评估的区别

直接改 harness 而不试跑时，没有经验库的代码任务分数从 73.4 降到 63.2；已有经验可以降低这种盲改风险。另一个留一复用实验用完成后的库，排除当前任务自己的条目，令 WorkBuddy 从 77.5 提升到 79.4、JobBench 从 36.0 提升到 37.7。后者允许利用时间上更晚任务形成的经验，属于回顾性可复用性测量，不等于在线任务流的实时结果。

执行更短，不等于全流程更便宜

主表某些配置中执行步数下降，例如 Gemini / OpenCode 从 25.4 到 21.9；该步数是最终执行会话的指标，不包含所有提出、试跑和综合。图 6 另外按交付前全部执行器与改进器 token 比较质量—成本曲线，才接近方法的实际计算代价。JobBench 的工具错误率从 14.4% 降至 9.1%，工具调用次数却从 27.4 升至 32.8，也说明更可靠的工具行为不必意味着调用更少。

边界：行为对比不能替代真值

最实质的局限是共享错误和选择错误。附录给出选择器把评分 95 的候选放弃而选中 55 分结果的例子，也有候选共同保留错误前提、最终退步 2–11 分的情况。因为改进器没有真实评分，它只能从可见要求和行为迹象推断质量；在输出表面完整、核心事实错误的任务中，这种推断尤其脆弱。

经验库也不是越大必然越好。相似任务检索、旧经验的适用条件、冲突规则及维护成本都影响长期效果。论文展示的是有限任务流和若干跨基准复用，没有证明任意长度任务流上的持续改善，也没有证明无限增加 k 会单调提升。图中的 k = 1–5 趋势应限定在测试过的设置。

对实际应用而言，我会把它理解为一种“可试跑的运行程序优化”。适合产物可检查、环境可重置、额外计算可接受的工作任务；若执行会产生不可撤销的现实副作用，候选试跑不能直接照搬。进一步验证应报告全流程时延和费用，区分选错、候选本身错误与经验误用，并用独立事实核验衡量“轨迹看起来更规范”是否真的带来更可靠的结果。
