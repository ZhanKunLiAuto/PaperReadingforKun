ThinkJev

一次思考如何支持不同预算，以及置信度为何还不够

Xiaolu Ding 等 · 31 页2026-10-27 · 用户提供的 PDF 版本

ThinkJev 提供的是一套可复用的推理预算接口，同时也是一份重要的负结果：直接回答、完整思考和中途停止都输出同一个有限选项空间上的概率，因而可以比较、校准和路由；但“直接回答有多自信”仍不足以判断“这次思考究竟值不值得”。在核心测试中，方法降低了平均思考 token，却没有达到事先设定的“基本保住准确率，同时最多让一半问题进入思考”的联合目标。

最值得保留的贡献有两层。工程上，共享提示前缀和单条思考轨迹让不同预算的决策可以在一致接口下实现。研究上，论文把校准、风险控制、节约计算与实际思考收益拆开测量，显示一个概率即使校准良好，也未必是好的计算分配信号。预测自己会不会错，与预测再想一会能不能改对，是两个不同问题。

关键概念：有限选项让“不确定”可以测量

Typed decision 指模型从 2–16 个明确选项中作出决定，每个选项映射到单个字母 token。系统读取这些字母的 logit，再归一化成选项概率，而不是解析一段自由文本来猜答案。这样同一套准确率、负对数似然和校准指标可以用于不同任务，但结论范围也限定为能够可靠编码到这些选项的决策。

S1 是不生成思考文本的直接决策；S2 是经过思考再读出同一组选项。温度缩放在开发集上拟合标量 T，再以 softmax(logits / T) 生成概率。这里的温度是概率校准参数，与生成思考时的采样温度不是一回事。ECE 衡量分箱后信心与准确率的差距，但低 ECE 不自动保证每个任务族、每个置信水平或新分布都可靠。

门控先判断 S1 是否足够可信；否则进入思考。Anytime 则允许在思考途中若干检查点停止。风险认证是另一种选择规则：只对满足开发集统计检验的 S1 接受区域作风险承诺，不是声称整个系统每次回答都有确定的错误上界。

核心问题：怎样知道额外思考值得付费

理想路由器不是把所有困难题都交给思考，而是识别额外计算带来的净收益：哪些 S1 错误会被思考修复，哪些本来正确的回答会被越想越错，哪些难题想很久也没有改变。只预测 S1 正确性，缺少后两种信息。

论文在主模型测试集上观察到，完整思考修复了 1,971 个直接决策错误，也把 260 个原本正确的回答变成错误。常规任务块中，修复 183 个的同时损坏 99 个。这使“低置信就多想、高置信就结束”具有不对称代价：有些便宜的直接回答已经足够好，有些低信心问题却几乎没有思考收益。

要研究这个问题，首先需要让不同预算的输出可比。若每种预算用不同自由文本格式、不同提示或独立随机思考，观察到的差别会混合格式、随机性与预算。ThinkJev 用共享前缀、同一条思考路径和统一字母概率读出，尽量把比较集中到“思考到这里时，决策改变了多少”。

机制：一条思考轨迹，不同停止预算

每个预算都读取相同的选项概率，但有各自拟合的校准参数。检查点读出使用复制缓存，不改变继续生成的原始思考。

S1 直接决策

题目 + 有限选项
→
共享 token 前缀缓存
→
直接模板 + 字母 logits
→
温度校准 → 接受或升级

可对选项做循环置换并几何平均映射后的概率，以减少位置偏差；这增加短前向计算，不是完全免费。

S2 完整思考

保留原始前缀缓存
→
采样一条思考，最多 4096 token
→
自然结束 / 提示结束
→
同样字母读出 + 独立校准

使用一个由样本标识设定种子的思考轨迹。完整思考与直接决策共享输入前缀，但读出模板和校准参数不同。

途中预算检查

原始轨迹继续生成
→
128 / 256 / 512 / 1024 / 2048 等检查点
→
复制缓存 + 早停提示 → 选项概率
→
达到阈值就停止，否则继续原轨迹

复制分支用于测量，不把早停提示写回继续思考的原始缓存。token 节省不包含所有短读出和复制开销。

风险控制的另一条规则

开发集按组统计 S1 错误
→
从严格到宽松检验阈值
→
仅接受通过检验的区域
→
其余问题交给 S2

保证依赖相同分布和统计分组假设，适用于接受的 S1 子集；它不直接认证后续 S2 的错误率。

共享的是实际 token 前缀，而不是肉眼相同的字符串

S1 与思考模板取最长相同 token 前缀，先只计算一次。Qwen3.5 的边界受分词影响，未必正好落在看起来像思考起点的文字位置；其循环状态也不能任意回滚，因此需要复制缓存来读取 S1 或中途答案，再保留原缓存继续生成。模型和缓存实现决定这一步能否正确复用。

S2 使用采样温度 0.6、top-p 0.95、top-k 20，最多 4,096 个思考 token。系统在 0、128、256、512、1,024、2,048 及完整轨迹处评估。到达检查点时，复制缓存、追加结束提示、读出选项。若采样种子、前缀和数值行为保持一致，一条长轨迹的前缀可以用于对应短预算比较；这不是说所有重新采样的短思考都会得到同一答案。t = 0 的早停模板与直接 S1 也不同，只能实测比较，不能数学上视为相同。

位置校正和预算校准各解决一种偏差

对 K 个选项，循环移动选项顺序并对映射回原选项的 log 概率求平均，相当于几何平均，可以抵消理想化的加性位置偏差。代价是额外 K−1 次短前向计算。主模型 S1 准确率由 62.2% 提至 64.2%，ECE 从 0.027 变为 0.024。这个改进不能描述为同样一次前向里免费获得。

不同思考长度分别拟合温度，因原始信心随预算变化。主模型的校准温度从 t = 0 的 1.61 升至完整思考的 4.07，说明更多思考会让原始概率变得更尖锐，程度超过正确率增长。若部署在新预算上直接复用一个温度，就失去了论文实际验证的条件。

阈值怎么选择，以及什么被“认证”

主门控在开发集上寻找节约 token 的阈值，同时将相对 always-think 的准确率损失限制在 ε，主设置 ε = 1 个百分点。Anytime 在各检查点使用对应校准和停止阈值。全流程不训练基础模型参数，但温度、门控阈值依赖带标签开发集；因此“无需模型训练”不能写成“无需监督数据”。

风险控制使用 Learn-Then-Test 思路，以 δ = 0.05、目标错误风险 1%、2%、5%、10% 检验接受阈值。作者采用单侧 Clopper–Pearson 上界、按模板组折算有效样本，并从严到宽进行固定序列检验。1% 风险即使零错误也需要约 300 个有效组才可能通过，所以低风险时接受率为零并不奇怪。统计保证还依赖开发和测试间的适用分布假设；不能将其理解成任意分布或单次回答的确定性保障。

证据：节省了一部分计算，但预设联合目标未实现

主数据含 5,582 个开发样本、8,359 个测试样本，按模板组哈希作 40 / 60 切分，避免同模板直接跨集合。测试分为常规任务 A（2,626）、公开推理 B（2,487）、生成任务及国际象棋 C（3,246）；生成部分覆盖日期、计数、规则链、否定、算术、逻辑、图与调度，并包含中英文。公开题库可能有预训练污染，模板分组也不能解决所有语义近似泄漏。

前 256 token 的平均收益有限，之后明显增加；每个检查点分别校准后的 ECE 约 0.017–0.036。这说明概率可以保持相对可用，但“校准了”并不意味着系统很早就能作出好答案。日期和算术问题几乎全部升级，S1 约 35.5% / 37.5%，思考后达 99% / 100%；国际象棋也约 97.8% 升级，却只从 40.4% 到 45.8%。相同的高升级率对应完全不同的收益。

风险、覆盖率与路由质量是不同轴

在 5% 风险目标下，27B 主模型接受 24.5% 的 S1 决策，测试风险为 3.9%，报告区间 [3.1%, 4.8%]；4B 覆盖仅 6.5%，9B 为 0。更严格的 1% 目标下主模型也不接受任何样本。Qwen3.8 的一个 10% 目标设置测试风险为 10.5%，报告区间为 [9.5%, 11.7%]，提醒我们统计控制不是每次数据实现都不越界。测试区间以决策独立近似计算，通常又比模板组层面的区间更窄，应与方法的分组假设区分。

直接问模型是否值得思考的 zero-shot 路由在主模型上，归一化路由面积为 0.491，高于置信度门控的 0.436；前缀探针与 n-gram 路由也没有稳定解决问题。最好的方法仍只取得不到理想 oracle 优势的一半。学习“直接答案是否正确”与学习“思考的增量价值”之间仍有明显距离。

token 与真实延迟不能直接互换

延迟只在 4B、H200、batch = 1、600 个测试样本上测量：共享前缀预填充约 101 ms，缓存复制和 S1 读出约 53 ms，位置旋转约 164 ms；完整思考中位数为 30.3 秒、1,038 token。共享前缀确实避免重复计算，但相对长思考总时间只是小部分。Anytime 的思考 token 不包含所有检查点短读出，72% token 不能直接宣布为 28% 端到端提速。

后续探索性 JevBench 使用 231 个公开问题及其中 111 个较难子集，不再拟合阈值。27B 门控在全体上为 224/231，完整思考为 226/231，升级率 29.4%，token 从 1,307 降到 742。这是更有利的分布结果，但发生在主实验之后，不能替代原先预注册目标的失败；小样本差异不显著也不是等效性证明。

边界与下一步：校准接口有价值，收益预测仍待解决

ThinkJev 很好地把推理预算变成可观察、可校准的系统变量。但有限选项、选项 token 化、模板组切分、特定开源模型与缓存实现共同限定了适用范围。自由生成代码、长篇写作和开放世界行动没有现成的 2–16 个答案，不能直接照搬这里的风险保证。

未来路由应估计不同预算下的收益和成本：不仅问 S1 会不会错，还问思考能否修复、是否会破坏，以及多长时间后仍没有有效进展。当前结果也提示不能只优化总平均，日期、棋类和日常决策的收益结构差别很大，应按任务族和分布变化检查。

我的判断是：这篇论文值得作为构建可比较推理系统的方法参考，也值得作为“更可靠的概率并不自动带来更好的算力调度”的实证提醒。部署时应保留独立校准、明确预算计费和接受区域的风险解释，再用实际延迟与任务收益决定是否采用，不能只拿 token 下降替代业务价值。
