SAME MODEL · FIXED WEIGHTS · EVIDENCE-GROUNDED HARNESS EDITS

Self-Harness

它问的不是“更强模型能否替弱模型写一个好 Agent”，而是更难也更具体的问题：让当前这个固定模型在现有支架里跑任务、观察自己反复失败的方式，再由同一个模型提出下一版支架，是否仍能得到可回归验证的稳定提升？

Hangfan Zhang、Shao Zhang、Kangcong Li 等 8 位作者 上海人工智能实验室 arXiv v3 · 31 页 · v1 提交于 2026-06-08
研究目的

降低为每个新模型手工重写 Agent harness 的工程成本，也摆脱“总要找一个更强外部优化器”的前提：固定模型权重、工具、预算、环境和 evaluator，只允许当前模型根据自己的 held-in 失败证据修改声明过的支架表面；再用 held-in 与未向 proposer 展示轨迹的 held-out 任务做保守回归，检验这种同模型自改能否跨模型家族与任务环境稳定生效。

核心结论

第一，论文确实证明“同一个模型可以参与修自己的支架”。MiniMax M2.5、Qwen3.5-35B-A3B 与 GLM-5 都同时扮演任务执行者和 proposer；权重、工具、预算、环境与 evaluator 固定，只改 DeepAgent harness definition。

第二，收益不是来自统一神奇 prompt，而是模型 × 环境的补偿层。Terminal-Bench 需要早落盘、打断工具循环和持久化环境；SWE-bench 需要 diff / 目标测试 / 依赖恢复；AppWorld 需要分页穷举、时间边界和 action-only completion semantics。

第三，最关键的机制不是“会提建议”，而是保守晋升。候选必须 held-in 不降、held-out 不降，并至少一侧 pass count 上升；否则即使总通过数更高也拒绝。两次重复降低了单次幸运晋升，但仍不是充分的统计检验。

第四，这篇 v3 与仓库已有的 Don't Train the Model, Evolve the Harness 不是同一工作。后者由更强外部 proposer 优化另一个目标模型，并聚焦法律任务；Self-Harness 的贡献正是把 proposer 换成目标模型自身，并扩展到三类 agent benchmark。

WHO IMPROVES WHOM

三个范式只差一个角色，却对应三种完全不同的主张

HARNESS（运行支架 / 执行外壳）

英译中：位于固定模型和环境之间的非参数系统层，包括系统提示、工具、memory、verification rule、permission、adapter、runtime control 和 failure recovery。

怎么理解：它不改变模型权重，却决定模型能看见什么、能做什么、错误后怎样恢复、什么时候结束，以及怎样把结果交给 verifier。本文可编辑对象是一个声明清楚的 harness definition file，而不是任意重写 benchmark 或 evaluator。

SELF-HARNESS（自修支架）

英译中：目标模型在当前支架下观察自己的行为证据，并以 proposer 角色提出下一版支架。

避免误解：“self”只描述 proposer 与 task model 是同一个固定模型。失败归因、official verifier、candidate execution、split gate 和 merge 仍由外部评估框架编排，所以不是一个完全封闭、无外部反馈的自治循环。

HELD-IN / HELD-OUT（可见证据集 / 隐藏回归集）

英译中：held-in 的失败轨迹会进入 evidence bundle；held-out 的任务轨迹不展示给 proposer，只把 pass count 用作晋升 gate。

怎么理解：held-out 防止候选只修可见案例，但因为每个候选是否晋升都依赖它，它会间接塑造搜索路径。它比 held-in 更干净，却不等于一次性、搜索完成后才打开的 final test。

WHY SELF-REFLECTION IS NOT ENOUGH

旧瓶颈：一次失败只能讲故事，不能直接说明该改哪层支架

一个 verifier 说“缺少文件”，背后可能是三种完全不同的机制：模型从没识别交付物、编辑工具失败后删除了文件，或已经生成却放错路径。如果只按终局标签聚类，proposer 会得到“多提醒保存文件”这种粗糙答案，既可能无效，也可能破坏已能完成的任务。

模型特异性进一步放大问题。MiniMax 在 Terminal-Bench 容易长时间探索而不落盘，Qwen 会在编辑失败后重复动作并丢失 artifact，GLM-5 则会让环境安装只在当前 shell 有效。通用 prompt 也许同时提醒三件事，却会变长、互相干扰，而且无法验证真正修复了哪个故障。

最后是自我确认偏差。提出 edit 的模型很容易觉得自己的解释合理；若接受标准也是“proposer 认为会更好”，循环只会积累听起来正确的改动。论文因此把模型 rationale 降为 audit record，把 benchmark pass count 设为唯一晋升证据。

MINE → PROPOSE → REGRESSION-TEST → MERGE

机制链：模型负责提出假设，pass count 负责决定历史

第一步：把失败记录压成 evidence bundle

在第 t 轮，固定模型 M 在当前支架 ht 上运行 held-in 任务。每条记录 ri 包含任务 xi、执行 trace τi、输出 yi 与 evaluator 结果 zi。系统只对失败记录做三元归因 φ(ri)=(ci,qi,mi)，按完全一致的签名聚类，再按 support 和 actionability 排序，形成 Bt。

第二步：同一模型并行提出 K 个“窄改动”

Proposer 看到可编辑表面、失败模式、需要保留的 passing behavior 和过去尝试摘要，不直接吞整批原始轨迹。每个候选 (Δj,aj) 必须指定主要失败机制、改动表面、预期行为与回归风险；各分支在目标或机制上要有实质差异，但单分支只改解决问题所需的最小范围。

公式拆解 · Proposal Validation
Accept(Δj) ⇔ Δin(j) ≥ 0 ∧ Δho(j) ≥ 0 ∧ max(Δin(j), Δho(j)) > 0

这条式子回答：候选 ht(j)=Δj(ht) 什么时候有资格进入下一版支架？

Pin(h)
支架 h 在 held-in 上的通过任务数；它反映候选是否修到生成证据的那批行为。
Pho(h)
支架 h 在 held-out 回归集上的通过任务数；轨迹不向 proposer 展示，但分数参与晋升。
Δin(j)
Pin(ht(j))−Pin(ht)。允许为零，不允许为负。
Δho(j)
Pho(ht(j))−Pho(ht)。同样不允许牺牲回归集换 held-in 提升。
max > 0
至少一侧必须真的多通过一个或更多任务；两侧都打平不能靠“看起来合理”晋升。
直觉读法：这是一个 Pareto 式的保守门：只能向右上走，不能用一边的进步购买另一边的退步。它保护现有能力，却也会拒绝“先小退、组合后大涨”的候选，并反复读取 held-out 信号。

LIMITS, TEST CONTAMINATION, AND SAFETY

边界：它证明“能自提案”，没有证明“能无限自治”

证据较强

同模型支架编辑能稳定增益

九个模型—环境组合的最终支架两侧 split 都提升，且 trace 案例能对应到具体执行机制。

有条件成立

改动可以泛化到未展示轨迹

held-out 轨迹没有进入 evidence bundle，但分数反复进入晋升 gate，所以支持回归泛化，不是独立终测泛化。

尚未证明

自我改进能开放式扩展

搜索面、benchmark、verifier 和模型都固定；没有递归改 evaluator、获取新工具、改权重或跨域持续运行。

held-out 是回归 gate，不是最后一次才揭晓的测试集

候选虽然看不到 held-out 轨迹，却通过 accept / reject 反复收到 aggregate signal。搜索轮数越多，这个一位反馈越能对 split 形成选择压力。要强证“泛化”，应增加一个从未参与提案、排序、停止与调参的 final test，或在新 benchmark 上一次性迁移最终机制。

“没有更强外部 agent”不等于没有外部智能与规则

同一个模型确实负责提出 edit，这是论文最清楚的控制。但 evaluation system 负责 verifier-grounded attribution、signature construction、cluster ranking、candidate execution 和 acceptance；官方 benchmark verifier 还提供最终真值。系统摆脱的是更强 proposer，不是 evaluator、人工设计的可编辑表面或实验 scaffold。

最小初始支架让提升空间很大，也限制了对比

Baseline 是短 system prompt、DeepAgent 默认文件 / shell 工具和一组多数为空的声明接口。它适合观察机制从无到有，却不回答最终 Self-Harness 是否优于成熟手工 harness、Meta-Harness 或同预算的人类工程。尤其 AppWorld 的 40.6 点跃升，部分来自补上分页与 completion semantics 这类基础契约。

两次重复不足以完全消除 Agent 方差

不退化规则很保守，每个 candidate 又跑两次，比单次评分可靠；但 task 数有限，pass count 是离散变量，论文没有置信区间、配对检验或多重候选校正。候选恰好在两次尝试中不退化仍可能被晋升，微小提升也可能在下一轮消失。

单候选安全，不自动推出合并安全

同轮多个兼容候选分别通过后会合并。两个单独无害的 prompt、middleware 或 subagent 可能互相放大预算、冲突或改变终止行为。算法下一轮会重新评估 ht+1，但更严谨的实现应在真正激活前对“合并后的整体”再执行同一 gate。

搜索成本和停止标准没有形成完整账本

附录给出 MiniMax / OpenRouter 托管服务、Qwen 在 4×H200 本地部署、Terminal 2MB/s 网络上限、SWE 3,600 秒 case timeout / 120 秒 tool timeout、AppWorld 50 turns 等环境信息；但没有把 K、T、候选总数、token、GPU 小时和 API 成本统一报告。与人工或外部优化器比较时，这些成本不可缺。

更高风险的支架改动需要比 pass rate 更强的门

实验只允许修改声明过的 harness file，并以 benchmark 成功为目标，风险相对可控。若支架能改变网络权限、秘密管理、删除策略、支付动作或 evaluator，本模型可能提出“更高分但更危险”的机制；此时需要权限不变量、安全测试、人工审批、可回滚发布和独立审计，而不能只靠任务 pass 不退化。

与已有 harness 进化工作的准确关系

Self-Harness 没有否定 Meta-Harness，也没有重复“支架会影响模型成绩”这个已知结论。它新增的实验变量是 proposer 身份：在没有更强外部 agent 的前提下，目标模型能否从结构化证据提出对自己有效的 bounded edit。论文尚未直接比较同一任务、同一预算下 self proposer 与 stronger proposer 谁更好。

一句话判断：Self-Harness 最成熟的读法不是“Agent 已经能自我进化”，而是“把同模型诊断变成假设生成，把独立 verifier 变成保守合并门”。真正可复用的是这套证据纪律，而不是让模型自由修改自己的运行环境。
